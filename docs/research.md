# Исследование AI-подхода для Reviews Analyzer

Евгений Агарков · роль «Модель» / AI Engineer · лабораторная № 1 · 21.11.2026.

**Статус:** исследование, сравнение кандидатов и реальные локальные эксперименты выполнены.
Проверены три промпта Qwen3-4B-4bit: 180 генераций на 20 синтетических отзывах,
плюс один smoke-запрос. API Яндекса подключён проверкой списка моделей; генерация
в облаке не запускалась из-за ограничения пользователя «только бесплатно» и отсутствия
отображаемого гранта. Локальная модель не достигла всех целей продукта.

## 1. Вопрос и границы

Как из ≤100 русскоязычных отзывов об одежде и текстиле получить проверяемый список
проблем с частотой, серьёзностью, цитатами и следующим действием?
Основание — [PRD](prd.md), боли P1–P5 и пределы 180 секунд / 50 ₽ на пакет.
Загрузка CSV, проверка обязательных полей и публикация интерфейса относятся к общему
приложению; эта работа проверяет подход к разбору текста.

Ответы клиентам, автоматический сбор, создание задач во внешних сервисах и
непрерывный мониторинг исключены из MVP по PRD. Существующие поля `reply` в golden
не превращаются в обязательную функцию модели.

## 2. Воронка исследования

### Узкий этап: проблема и уже существующие решения

Ozon рекомендует продавцам отслеживать рейтинги и отзывы в составе продуктовых
метрик [S1]. Это подтверждает релевантность категории задачи, но **не доказывает**,
что выбранные продавцы готовы платить за наш продукт. Интервью и наблюдения
реальных продавцов в рамках этой работы не проводились.

Сопоставлены три альтернативы:

| Вариант | Что доступно | Вывод для проекта |
|---|---|---|
| Ручной разбор файла | Человек читает текст и выписывает жалобы | Контрольный способ для будущего учебного эксперимента; его скорость пока не измерена |
| Кабинет Ozon Seller | В официальном обзоре есть работа с отзывами, сортировка по оценкам/статусам [S2] | Реальная альтернатива в рамках одной площадки. Отсутствие семантической группировки в продукте этим обзором не доказано |
| Инструменты Яндекс Товаров | Официальный гайд описывает анализ отзывов и динамики рейтинга [S3] | Аналоги уже существуют; новизна нашего решения и спрос пока не подтверждены |

Рабочая гипотеза отличия Reviews Analyzer: одинаковый CSV-сценарий для нескольких
площадок, привязка каждой проблемы к цитатам и действиям. Это проектная гипотеза
из PRD, которую ещё нужно проверять сравнением с реальными рабочими процессами.

### Широкий этап: подходы

| Подход | Ожидаемая польза | Ограничения и решение |
|---|---|---|
| Правила / словарь | Дешёвый воспроизводимый нижний ориентир | Выполненные прогоны показали зависимость от формулировок; сохранить как baseline, не выбирать основным анализатором [E1] |
| Классификатор тональности | Метка общего отношения к товару | Одна тональность не даёт набор проблем, цитаты и действия; RuReviews размечен для sentiment, а не всей нашей задачи [S4] |
| Прямой LLM-промпт → JSON | Один разбор может извлечь несколько аспектов текста | JSON-формат не гарантирует правильный смысл. Нужны проверки схемы и цитат; поддержку структурированного вывода описывают провайдеры [S5, S6] |
| Эмбеддинги + кластеризация | Возможный способ искать близкие формулировки | Отдельно не определяют тяжесть и основания рекомендаций. Отложить до измерения ошибок фиксированной таксономии; это инженерный выбор, не доказанное превосходство |
| RAG | Подключение внешних знаний; исходная работа рассматривает retrieval для knowledge-intensive задач [S7] | В MVP основание уже находится в загруженных отзывах; дополнительного корпуса нет. На первом этапе не нужен |
| Агент с инструментами | Может выполнять многошаговые внешние действия | В текущем сценарии внешние действия отложены. Дополнительные вызовы усложнят стоимость и проверку; агент пока не нужен |

### Узкий этап: проверка выбранного направления

1. Для семантики сравнить три [кандидата](model-candidates.md), не подменять
   benchmark собственной оценкой «модель хорошо знает русский».
2. Выполнены `rules-v0`, исправленный `rules-v1` и диагностический challenge:
   [протокол, команды и результаты](experiments/lab1.md).
3. Выполнены P0 (минимальная инструкция), P1 (правила и псевдосхема) и P2
   (валидный пример JSON, точные определения и цитаты). [Результаты](experiments/local-results.md):
   P2 исправил тип null и поднял precision на golden до 83,3%, но recall остался
   83,3%, дословность цитат — 8/12, critical — 0/1. Для продукта этого недостаточно.
4. На следующем этапе Quality должен независимо дополнить эталон, чтобы выбор
   не опирался только на примеры, по которым настраивались промпты и baseline.

## 3. Предлагаемый путь запроса

`CSV → валидация строк → подтверждённые отзывы → порции для LLM → JSON`
`→ проверка схемы и цитат → агрегация кодом → сортировка → отчёт`

Это схема предлагаемого MVP, а не заявление о готовой реализации.

- Вход содержит `platform`, `review_id`, `product_id`, `rating`, `text`.
- У каждой найденной проблемы: код из таксономии, точная цитата, серьёзность,
  предполагаемый ответственный, основанное на тексте действие. В пилотном
  формате v0.1 серьёзность/owner ещё относятся ко всему отзыву — это ограничение.
- Частоты, доли, дедупликация и сортировка считаются обычным кодом, без LLM.
- Ключ группировки — `(platform, product_id, problem_code)`, не просто код проблемы.
  Один `review_id` на площадке даёт не более одного упоминания одного кода.
- Каждую цитату сверяем с исходным текстом после нормализации пробелов. Отсутствующая
  цитата блокирует вывод. Совпадение строки необходимо, но смысл проверяется отдельно.
- Сначала critical, затем high, medium, low; внутри уровня — частота. Серьёзность
  означает описанный риск, а не установленный факт вреда или медицинский диагноз.
- Проблемы вне таксономии нельзя молча терять: в следующем контракте нужна отметка
  `needs_review`, пример и пересмотр таксономии вместе с Quality; текущий пилот
  проверяет только известные коды и не решает open-set detection.

## 4. Безопасность и ошибки

Отзывы — недоверенные данные. Prompt injection остаётся отдельным риском для LLM
[S8]. Инструкция P1 отделяет правила от отзыва; никакого доступа к инструментам
и публикации у пилота нет. Наличие `has_instruction=true` само по себе не доказывает,
что атака не исполнена. Это требует проверки фактического ответа и дополнительных атак.

План для приложения: валидировать JSON и ссылки на исходные отзывы, ограничить
число токенов и общий расход, иметь deadline на пакет. При отказе/таймауте/неполном
разборе показывать явную ошибку; не выдавать частичный результат за полный.
Повтор — максимум один в заранее зарезервированном бюджете. В пилотном runner
повторов нет: потерянный ответ может быть уже оплачен. Он не является production API.

## 5. Данные, лицензии и расхождения

- Для запусков взят **неизменённый** синтетический golden-v0.1 (12 записей) из
  коммита `5bf0a368fe15d4395d8b5b8daf32efe2fa7c58cb`. Хеш записан в результатах.
- RuReviews: просмотрены README и LICENSE исходного репозитория; лицензия
  репозитория Apache-2.0 [S4]. Внешние тексты не скачивались и не включались в
  прогоны. При будущем использовании сохранить атрибуцию/лицензию и отдельно
  проверить персональные данные и применимость условий к выбранным данным.
- Qwen3-8B публикуется с Apache-2.0 [S9]. Это лицензия модели, не лицензия отзывов.
- У golden нет `product_id` и отдельного входного `review_id`; `id` записи используется
  только для сопоставления метрик. Поэтому групповая проверка из PRD невозможна.
- `gd-0002` и `gd-0003` имеют один grouping-тег, но разные площадки. Одинаковый код
  можно проверять; объединять эти отзывы в одну товарную группу нельзя.
- Критерии Quality ещё описывают ответы клиентам, поток за 24 часа и порог цитат 90%;
  актуальный PRD откладывает ответы/мониторинг и требует 100% существующих цитат.
  Для этого исследования приоритет имеет PRD. Исходные документы Quality не изменены.
- На весь отзыв задан один `owner`, хотя товар и доставка могут упоминаться вместе.
  Нужна разметка на уровне проблемы. Один код `material_quality` объединяет и усадку,
  и катышки: этого мало для точных названий повторяющихся дефектов. Детализацию
  нужно согласовать с Product/Quality, не менять эталон ради улучшения цифр.

## 6. Решение / ADR-001

**Выбрать для дальнейшего прототипирования:** прямое извлечение через промпт,
контракт вывода, внешние проверки цитат и детерминированную агрегацию. Для учебных
проб выбран **локальный Qwen3-4B-4bit + P2**, потому что это реально доступный
бесплатный вариант на M1 Pro / 16 GB. Выбор production-модели остаётся открытым.

**Основание:** правила провалились на новых формулировках [E1]; LLM нашла часть
перефраз без расширения словаря. P2 дал 100% валидности схемы на обоих наборах,
но не устранил ошибки смысла и пропуски critical. [Таблицы](experiments/local-results.md)
показывают и улучшения, и провалы. Это подтверждает полезность семантического этапа,
но не готовность именно этой модели к приёмке продукта.

P2 выбран как более ясный начальный контракт, а не победитель по всем метрикам:
на challenge critical у P1 был 1/1 по уровню, а у P2 — 0/1. Нельзя скрывать эту регрессию.
Дополнительный поиск внешнего корпуса не следует из текущей задачи PRD.

**Цена решения:** локальная установка заняла около 3,3 GB; пик MLX в P2 около 3,24 GB,
запросы выполнялись примерно за 4–6 секунд. Более длинный промпт увеличил latency.
Квантизованная небольшая модель ошибается в серьёзности, кодах, зонах ответственности
и регистре цитат; для MVP потребуется независимая проверка, возможно другой размер
модели/режим и более строгий контракт. Локальность убирает плату за облачные токены,
но не стоимость электричества и оборудования. Для облачного варианта сохраняются
API-зависимость, тарифы, квоты и необходимость обработки отказов.

**Альтернативы:** правила оставить контрольным baseline; RAG отложить до появления
внешних инструкций/политик; агента — до разрешённых действий; дообучение — до
достаточных данных и доказанной необходимости. 12 знакомых примеров недостаточны.

**Пересмотр:** после независимого набора Quality, следующей проверки модели/контракта
и измерения пакета 100 отзывов. Текущие P0/P1/P2-пробы этого не заменяют.
Критерии: precision ≥80%, recall ≥85%, цитаты 100%, ни одного пропуска critical,
owner ≥85%, ≤180 секунд, ≤50 ₽. North Star проверяется отдельно с людьми.
Нулевой знаменатель или неподходящий датасет означает «нет данных», не успех.

## 7. Реестр проверенных источников

Проверено 21.11.2026; источники прочитаны агентом, финальная проверка автором перед
сдачей ещё нужна. Источники описывают возможности, а не качество нашей реализации.

- **S1:** [Ozon: ключевые метрики](https://seller.ozon.ru/media/beginners/za-kakimi-pokazatelyami-analitiki-nuzhno-sledit-prodavcu/) — релевантность отзывов продавцам.
- **S2:** [Ozon: кабинет продавца](https://seller.ozon.ru/media/beginners/kak-ustroen-lichnyj-kabinet-prodavca-ozon-obzor-versii-dlya-kompyutera/) — существующий процесс работы с отзывами; обзор не доказывает текущую полноту функций.
- **S3:** [Яндекс: работа с репутацией](https://yard.yandex.ru/courses/kurs-poisk-i-tovary/gayd-kak-rabotat-s-reputaciey) — инструменты анализа отзывов/рейтинга.
- **S4:** [RuReviews](https://github.com/sismetanin/rureviews), [LICENSE](https://github.com/sismetanin/rureviews/blob/master/LICENSE) — назначение датасета и условия репозитория.
- **S5:** [Yandex: формат вывода](https://aistudio.yandex.ru/en/docs/ai-studio/concepts/generation/structured-output) — JSON/структура ответа; совместимость проверять для конкретного API/модели.
- **S6:** [Gemini: structured outputs](https://ai.google.dev/gemini-api/docs/structured-output) — извлечение структурированных данных.
- **S7:** [Lewis et al., RAG](https://arxiv.org/abs/2005.11401) — подход retrieval + generation, не benchmark нашего сценария.
- **S8:** [OWASP: Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) — риск инструкций в недоверенных данных.
- **S9:** [Qwen3-8B](https://huggingface.co/Qwen/Qwen3-8B), [LICENSE](https://huggingface.co/Qwen/Qwen3-8B/blob/main/LICENSE) — локальный кандидат и лицензия.
- **E1:** [Наши эксперименты](experiments/lab1.md) — собственные фактические результаты, не внешний источник.

Актуальные тарифы, URI и отключение старых моделей приведены в
[сравнении кандидатов](model-candidates.md). Публичный отчёт о спросе и независимое
сравнение точности LLM по этому исследованию делать нельзя.

зафиксированы вместе с результатами. 4-bit результат не переносится автоматически
