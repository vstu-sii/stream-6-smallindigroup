# Общий словарь Reviews Analyzer

Единые определения для требований, интерфейса, анализа отзывов и эталонных примеров.

| Термин | Что означает в нашем проекте |
|---|---|
| Сегмент | Выбранная группа пользователей с похожим процессом: небольшие продавцы одежды, тканей и текстиля на маркетплейсах, которые сами разбирают отзывы |
| Продавец | Пользователь продукта, принимающий решение о проверке товара, изменении описания или обращении к площадке; это не автор покупательского отзыва |
| Маркетплейс | Торговая площадка: Wildberries, Ozon или Яндекс Маркет; во входе — `platform` |
| Товарная позиция | Конкретный товар в магазине, по которому отдельно собираются и считаются проблемы; во входе — `product_id` вместе с `platform`, чтобы различать товары разных площадок |
| Отзыв | Один текст покупателя с идентификатором, оценкой и привязкой к площадке и товару; во входе — `platform`, `review_id`, `rating`, `text` |
| Пакет отзывов | Набор, который пользователь загружает и обрабатывает за один раз; в первой версии — до 100 отзывов |
| CSV | Текстовый формат таблицы; в нашем входном файле одна строка соответствует одному отзыву |
| Проблема | Описанный в отзыве недостаток или затруднение, которое нужно показать пользователю; один отзыв может содержать несколько проблем |
| Код проблемы | Устойчивое техническое имя типа проблемы; `problems[].code`, например `material_quality` |
| Таксономия | Словарь кодов проблем и правил, по которым жалоба относится к определённому типу |
| Перефраз | Другая формулировка той же проблемы: например, «село после стирки» и «стало меньше после машинки» |
| Группировка | Объединение перефраз одной проблемы внутри одной товарной позиции с учётом площадки; жалобы на разные товары не смешиваются |
| Упоминание проблемы | Один отзыв, в котором найден конкретный код проблемы; повтор одной жалобы внутри текста не увеличивает её счётчик |
| Частота проблемы | Число разных отзывов с проблемой; доля равна этому числу, делённому на число принятых для анализа отзывов того же товара на той же площадке |
| Цитата / улика | Фрагмент исходного отзыва, которым подтверждается вывод; техническое поле — `evidence`. Выдуманный или изменённый текст не считается цитатой |
| Серьёзность | Тяжесть описанных последствий конкретной проблемы; `problems[].severity`: `low`, `medium`, `high`, `critical`. Если проблем не найдено, используется пустой массив, а не серьёзность `none` |
| Критический сигнал | Указание в тексте на возможные особо тяжёлые последствия; показывается человеку отдельно и не является доказательством вреда |
| Приоритет | Порядок проблем в отчёте: сначала более серьёзные, затем более частые внутри уровня серьёзности |
| Зона ответственности | Предположение о том, кто может влиять на устранение причины: продавец или площадка; `owner`: `seller`, `marketplace`, `null` при неопределённости. Это не установление вины |
| Подозрительный отзыв | Отзыв с признаками, требующими проверки; `suspicious`. Пометка не доказывает накрутку и не исключает отзыв автоматически |
| Отчёт | Результат разбора: проблемы по товарам, частота, серьёзность, цитаты, зона ответственности и подсказки действий |
| Действие | Выбранный человеком конкретный следующий шаг, связанный с подтверждённой проблемой; например, проверить размер образца после стирки |
| MVP | Первая ограниченная работающая версия: загрузка файла и отчёт. Интеграции и публикация ответов в неё не входят |
| North Star | Главная метрика учебного проекта: доля заданий, в которых участник команды или однокурсник за 10 минут выбрал обоснованное действие по отчёту; цель — не ниже 80%. Она оценивает выполнение сценария, а не спрос продавцов |
| Golden dataset | Версия набора отзывов с заранее подготовленными правильными ответами для проверки системы; владелец — Quality |
| Эталон | Ожидаемый результат для конкретного проверочного примера, поле `expected`; он определяется до прогона системы |
| Полнота / recall | Доля найденных верных пар «отзыв, код проблемы» среди всех эталонных пар; цель — не ниже 85% |
| Точность / precision | Доля верных пар «отзыв, код проблемы» среди всех пар, которые выдала система; цель — не ниже 80% |
| Запрос и его стоимость | Одна полная операция анализа пакета. Для контрольного пакета 100 отзывов сумма всех обращений к модели, включая повторы, ограничена 50 ₽ |
| Инъекция инструкций | Попытка автора отзыва управлять системой текстом вроде «игнорируй правила»; такой текст остаётся данными и не выполняется как команда |

Новые коды и изменения значений обсуждаются Product, Quality и AI Engineer до изменения эталонов и реализации.

## Лабораторная 2: архитектура и AI-пайплайн

### Как читать дополнение

Термины ниже используются в [шести UC](use-cases/), [роадмапе](roadmap.md), архитектурном проектировании, исследовании AI Engineer и формате Quality v2.0. Словарь определяет общий язык; размещение частей системы, модель и её способ запуска закрепляются отдельными решениями команды.

В текущем формате у каждой проблемы собственные `problems[].severity`, `problems[].owner` и `problems[].evidence`. Короткие имена из основного словаря обозначают понятия. Значение `none` относится к историческому пилоту на уровне отзыва: в `problems[].severity` версии Quality v2.0 его нет; отсутствие найденных проблем передаётся как `problems: []`. Ошибка разбора не считается отсутствием проблем.

### Сценарии и архитектура

| Термин | Что означает в нашем проекте |
|---|---|
| Use case / UC | Цель продавца и последовательность действий до наблюдаемого результата. Определены UC-01–UC-06; отдельная кнопка или вызов API не равны пользовательской цели |
| Скоуп и не-скоуп | Скоуп — возможности, которые обязуется дать первая версия; не-скоуп — явно отложенные возможности. Их границы задаёт роадмап со ссылками на UC; наличие идеи в исследовании не включает её в MVP |
| Актёр | Роль вне рассматриваемой системы, взаимодействующая с ней. В наших UC основной актёр — продавец; Reviews Analyzer не выступает своим актёром |
| Проживаемость UC | Выполнение сценария человеком вне команды на макете или прототипе без уточняющих вопросов и подсказок. Проверяет понятность сценария; качество модели и North Star измеряются отдельно |
| Граница системы | Разделение между Reviews Analyzer и его окружением. В предложенной C4 Delivery внутри показаны web, API, воркер, модельный сервис, сервис хранения и БД. Продавец находится снаружи; кабинеты площадок не подключены. Внешний поставщик LLM, если он будет выбран, требует отдельного отражения зависимости |
| C4 | Способ описать архитектуру на уровнях system context, container, component и code. В lab2 нужны первые два: продукт с его окружением и приложения/хранилища внутри продукта с их связями |
| Контейнер C4 | Приложение или хранилище данных как отдельная часть архитектуры. Например, серверное приложение и БД. Это архитектурное понятие, которое не требует использования Docker |
| Компонент C4 | Часть внутри одного контейнера C4 с определённой обязанностью и интерфейсом. Например, модуль проверки данных внутри серверного приложения; отдельный процесс для такого модуля не обязателен |
| API и контракт API | API — способ программного взаимодействия частей. Контракт задаёт операции, входные данные, результаты и ошибки. Входной CSV, результат модели и HTTP-ответ связаны, но не обязаны быть одним и тем же объектом |
| HTTP-эндпоинт | Доступная операция HTTP API, определяемая методом и путём. Существующий `GET /health` проверяет доступность HTTP-приложения. `POST /internal/ai/reviews/analyze` уже описан проектом контракта, но его реализация пока не заявлена |
| OpenAPI | Стандарт машиночитаемого описания HTTP API: путей, методов, параметров, схем данных, ответов и ошибок. Путь контракта в задании — `api/openapi.yaml`; автоматическая страница Swagger не заменяет подготовку требуемого файла |
| Схема БД | Описание хранения: таблиц, полей, типов, связей и ограничений. Например, уникальность пары `platform` + `review_id`. Схема БД отличается от схемы ответа модели |
| ERD | Диаграмма сущностей и связей данных, например пакета, отзыва и найденной проблемы. Показывает устройство хранения; сама картинка не создаёт таблицы и миграции |
| ADR | Запись решения о структуре системы: где находятся обязанности и данные, кто от кого зависит. Содержит контекст, решение, альтернативы, цену и статус. Выбор модели, численного порога или скоупа сам по себе не является архитектурным ADR |
| Статус ADR | `proposed` — предложен для рассмотрения; `accepted` — фактически принят; `rejected` — отклонён с причиной. Если решение заменено, сохраняется ссылка на заменяющее решение. Статус не доказывает наличие готового кода |
| Цена решения | Дополнительная работа, расходы, ограничения и зависимости, возникающие из выбора. Для архитектуры учитываются сопровождение, время, стоимость, безопасность и сложность будущей замены |
| PlantUML | Текстовый язык описания диаграмм. Файл `.puml` является исходником; PNG или SVG — изображением, полученным из него |
| Контейнер Docker | Изолированная среда выполнения приложения на основе образа. В Compose lab2 выделены web, API, worker, model, storage и db; несколько из них пока являются заглушками. Это не определение контейнера C4 |
| Docker Compose | Описание совместного запуска сервисов и их настроек, сетей и томов. `compose.yaml` — каркас lab1, `compose.dev.yml` — шесть сервисов dev-стенда lab2. Готовность заглушек не подтверждает работающий AI-анализ |
| Health check | Проверка доступности или готовности конкретной части. `GET /health` у API подтверждает HTTP-доступность; заглушка storage дополнительно выполняет SQL-запрос к схеме. Ни одна из этих проверок не измеряет качество AI |
| aact | Инструмент проверки описанных архитектурных зависимостей по правилам. В проекте читает Container-диаграмму и `aact.config.ts`; отсутствие нарушений относится к проверенной модели связей и не доказывает работу AI или полноту UC |

### Данные и путь обработки

| Термин | Что означает в нашем проекте |
|---|---|
| Подтверждённый пакет | Корректные строки CSV, состав которых продавец явно принял по UC-01. Ошибки показаны до подтверждения; предположение о подозрительности не исключает строку |
| Ключ отзыва | Пара `platform` + `review_id`, по которой различаются отзывы. Совпадение `review_id` на разных площадках допустимо; повтор внутри площадки требует обработки как конфликт входа |
| Ключ группы | Тройка `platform` + `product_id` + `problems[].code`. Определяет, какие упоминания считаются вместе; одинаковый код у разных товаров не создаёт общую группу |
| AI-пайплайн | Путь данных от входа до отчёта: проверка CSV, подтверждение состава, разбор моделью, проверка результата и цитат, группировка, подсчёт и показ отчёта. Это общий путь обработки, а не обязательно цепочка из нескольких моделей |
| Воркер анализа / worker | Предложенная ADR-002 часть, которая выполняет разбор после постановки задания, отдельно от HTTP-запроса загрузки. Обращается к модели, проверяет основания и агрегирует результат; в dev-стенде пока работает заглушка |
| Сервис хранения / storage | Предложенная единая точка доступа к PostgreSQL. По C4 API и воркер обращаются к ней через внутренний HTTP-интерфейс; наличие readiness-проверки ещё не означает реализацию этих операций |
| Модельный сервис / model | Часть с внутренним HTTP-интерфейсом для разбора порций. Отличается от самих весов LLM: может содержать загрузку модели и проверки ответа. Текущая dev-заглушка веса не загружает; окончательный выбор модели этим именем не фиксируется |
| Задание / запуск анализа | Обработка одного подтверждённого пользовательского пакета с состоянием очереди, выполнения, полного, частичного результата или ошибки. В SQL ему соответствует `analysis_runs`; порции и попытки модели находятся внутри этого запуска |
| Атомарный захват задания | Выдача задания воркеру как одна неделимая операция, чтобы конкурирующие воркеры не начали его независимо. ADR требует такой реализации; её готовность не следует из наличия таблицы |
| Аренда задания / lease | Ограниченный срок, на который воркер получает задание. В схеме есть `lease_until`; после сбоя должна быть определена безопасная повторная выдача, исключающая конфликт записываемых результатов |
| Идемпотентность / Idempotency-Key | Повтор доставки того же запроса с тем же ключом и телом не запускает новую параллельную генерацию. Проект AI-контракта отделяет такой повтор от новой попытки генерации с новым ключом; все попытки остаются в бюджете пакета |
| Опрос состояния / polling | Повторное чтение состояния задания интерфейсом до готовности результата. Это не новая генерация и не основание повторно учитывать её цену; API должен различать ожидающий, неуспешный и доступный результат |
| LLM | Большая языковая модель, которая по инструкции анализирует текст и формирует ответ. Она может ошибаться даже при корректном JSON; для нашего результата нужны проверки структуры и оснований |
| Вызов модели / инференс | Один запуск модели на переданных инструкции и данных для получения ответа. Полный анализ пакета может включать несколько вызовов, расходы и время которых суммируются |
| Локальный запуск модели | Выполнение модели на компьютере или сервере, где размещены её веса и среда выполнения. Локальный пилот не определяет автоматически способ запуска итогового продукта; отсутствие платы за API не означает отсутствия затрат на оборудование |
| LLM-провайдер | Платформа, предоставляющая доступ к модели как сервису через API. При таком выборе появляется внешняя зависимость; локальный запуск модели не требует обязательного обращения к облачному провайдеру |
| Промпт | Инструкция модели с правилами разбора и переданными данными. Текст отзыва отделяется от управляющей инструкции и не получает право менять правила |
| Контекст модели | Информация, доступная модели в конкретном вызове: инструкция, таксономия, схема результата и переданные отзывы. Наличие полного пакета в приложении не означает, что каждый вызов модели видит его целиком |
| Порция для модели | Часть подтверждённого пакета, переданная за один вызов. Размер порции выбирается по ограничениям и замерам; он не равен автоматически размеру пользовательской загрузки или кейса-пакета Quality |
| JSON | Текстовый формат данных с объектами, массивами, строками, числами, логическими значениями и `null`. Синтаксически корректный JSON ещё может иметь неверные поля или содержать ложный вывод |
| Структурированный выход | Результат с заранее определёнными полями и типами, например список `problems`. Соответствие структуре проверяется отдельно от правильности найденных проблем |
| Кодовая точка и диапазон цитаты | AI-контракт задаёт непрерывный фрагмент как `text`, `start`, `end`: начало включено, конец не включён. Индексы считаются в Unicode-кодовых точках исходного текста, без нормализации; байты и UTF-16-единицы могут дать другие позиции |
| `analyzed` / `needs_review` | Состояния результата отдельного отзыва в проекте AI-API. Первое означает успешный разбор, в том числе без проблем; второе — явную неопределённость, требующую проверки. `needs_review` не агрегируется автоматически и не подменяется результатом «проблем нет» |
| Неполный отчёт / `incomplete` | В пакете есть принятые отзывы без пригодного завершённого разбора или требующие проверки. Общий флаг описан в Report API; объём неполноты и правило показа долей являются предметом уточнения при ревью ADR-002 |
| Валидация | Проверка данных на соответствие правилам. Для CSV — обязательные поля и допустимые значения; для ответа модели — формат и схема. Наличие цитаты в исходнике и смысл её связи с выводом — дополнительные проверки |
| Агрегация кодом | Подсчёт групп, разных отзывов, долей и порядка отчёта обычным программным кодом по результатам разбора. Модель размечает проблемы; итоговые счётчики и сортировку не доверяют её свободному тексту |
| Граница доверия | Место, где данные поступают из менее доверенного источника и должны быть проверены. CSV и ответ модели не становятся командами, исполняемым кодом или достоверным выводом только из-за получения |
| Контроль человеком / HITL | Продавец проверяет основания и принимает решение о следующем действии. В MVP модель не получает права публиковать ответы, отправлять обращения или создавать внешние задачи |
| Таймаут и срок запуска | Таймаут ограничивает ожидание операции; общий срок запуска ограничивает весь разбор пакета. Предел PRD 180 секунд отсчитывается от запуска анализа подтверждённого пакета до полного отчёта по 100 отзывам, включая необходимые повторы; ожидание действий человека до запуска не учитывается |
| Повтор / retry | Дополнительная попытка обращения после ошибки. Её время и возможная стоимость входят в общий бюджет запуска; повтор не должен быть бесконечным или скрывать незавершённый результат |
| Деградация / fallback | Заранее определённое поведение при недоступности основной возможности. Это может быть явный отказ или проверенный запасной режим; незаметная подмена слабым анализом не считается успешным полным результатом |
| Токен и токен-бюджет | Токен — единица представления текста моделью. Токен-бюджет ограничивает объём входа и выхода; из всех тарифицируемых токенов и тарифов считают расход, а предел 50 ₽ относится ко всему пакету |
| Лог | Запись отдельного технического события, например ошибки проверки или завершения вызова. Помогает искать неисправность; сам по себе не описывает весь путь пакета |
| Трассировка / трейс | Связанные записи шагов одного запуска с их порядком и длительностью. Позволяет восстановить путь пакета, вызовы, ошибки и повторы; набор несвязанных логов этого не гарантирует |

### Проверка качества

| Термин | Что означает в нашем проекте |
|---|---|
| Definition of Done / DoD | Проверяемые условия готовности артефакта или возможности: что должно существовать и каким способом это подтверждается. Подготовленный документ и согласованный командой документ могут иметь разные статусы готовности |
| Baseline | Исходный воспроизводимый подход, с которым сравнивают изменения. В исследовании есть правила и локальный LLM-пилот; baseline не означает достижение целевого качества MVP |
| Eval / прогон evals | Запуск зафиксированной версии подхода на эталонных входах с подсчётом ошибок и метрик. Проверка читаемости датасета не равна оценке ответов настоящей модели |
| Синтетический пример | Придуманный и явно помеченный отзыв или проверочная ситуация. Подходит для контролируемых проверок, но не выдаётся за реального покупателя или наблюдение; для H1 синтетика не используется |
| Атакующий пример / adversarial | Проверочный вход, намеренно пытающийся нарушить правила: скрыть жалобу, изменить серьёзность или вставить недопустимый текст. Это происхождение проверки, а не доказанный факт атаки реального покупателя |
| Кейс-пакет Quality | Набор отзывов и ожидаемый общий результат: состав групп, порядок и пометки. Проверяет взаимодействие отзывов в одном отчёте; отличается от порции, отправляемой модели |
| Диагностический пакет | Набор для изучения поведения и ошибок, который может содержать примеры для настройки. Его результаты отделяются от независимой итоговой оценки |
| Спайк | Короткий эксперимент на одно рискованное техническое допущение. Ответ «сработало / не сработало / иначе» фиксируется по реальному результату; план эксперимента не считается его выполнением |

### Имена полей Quality v2.0

Здесь зафиксирован смысл полей датасета. В `main` опубликованы проекты внутреннего AI-контракта и публичного отчёта OpenAPI 3.1.0, версия `0.2.0-draft`. Они описывают обмен, а не подтверждают реализацию эндпоинтов. Транспортный формат цитаты отличается от строки эталона и сопоставляется по правилам следующего раздела.

| Поле | Значение |
|---|---|
| `input` / `expected` | Вход проверочного примера / заранее подготовленный эталон. Поле `expected` не передаётся модели как правильный ответ во время проверки |
| `problems[]` | Найденные проблемы; у каждой свои `code`, `evidence`, `severity`, `owner`. Пустой массив означает, что при успешном разборе проблем не найдено |
| `problems[].severity` | `low`, `medium`, `high`, `critical`. Серьёзность группы определяется максимумом по входящим проблемам; значение `none` в это поле не записывается |
| `problems[].owner` | `seller`, `marketplace` или JSON-значение `null`. Не строка `"null"`; неопределённость не приравнивается автоматически к продавцу |
| `problems[].evidence` | Дословное основание из исходного отзыва. Пробелы нормализуются; несколько фрагментов разделяются ` ... `. Существование фрагмента и подтверждение смысла — разные проверки |
| `suspicious` | Логическая пометка подозрительного отзыва. При `true` отзыв сохраняется в знаменателе частоты, а его проблемы — в группах |
| `has_instruction` | В тексте обнаружена попытка управлять системой. Значение `true` не доказывает, что модель защитилась: отдельно проверяется фактический результат |
| `forbidden_in_output` | Список строк, которые не должны встречаться ни в одном поле AI-результата атакующего примера. Отдельный просмотр исходного отзыва как неисполняемых данных не является сгенерированным результатом и сам по себе не означает исполнения инструкции |
| `sentiment` | Диагностическая тональность текста: `positive`, `neutral`, `negative`, `mixed`. Она не равна оценке `rating` и не подменяет серьёзность проблемы |
| `split: tune` | Примеры, доступные для настройки промпта или подхода; не считаются независимой итоговой проверкой |
| `split: test` | Отделённые примеры для оценки зафиксированного подхода. Если по их ошибкам начали настраивать систему, для нового независимого вывода нужна новая проверочная выборка |
| `source.kind` | Происхождение записи: `synthetic` — придуманная, `adversarial` — атакующая, `public_review` — реальный открытый отзыв с сохранённым источником. Наличие значения в схеме не означает, что такие данные уже собраны |


### Коды проблем действующей таксономии

Коды взяты из формата Quality v2.0; новые коды этим словарём не вводятся.

| Код | Значение |
|---|---|
| `delivery_delay` | Доставка позже обещанного срока |
| `not_delivered` | Товар не получен |
| `wrong_item` | Пришло не то, что заказано: другой цвет, количество или модель |
| `defect_on_arrival` | Дефект замечен при получении, например дырка или пятно |
| `defect_after_use` | Дефект проявился после начала использования, например разошёлся шов |
| `material_quality` | Проблема ткани или материала, включая усадку, катышки и линьку; общий код не доказывает общую причину |
| `size_mismatch` | Размер не соответствует заявленной размерной сетке |
| `description_mismatch` | Характеристики или вид товара не соответствуют описанию либо фото |
| `smell` | Посторонний запах |
| `safety_hazard` | Описанный возможный вред здоровью или риск травмы; не установленный системой факт вреда |
