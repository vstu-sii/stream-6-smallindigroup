# План golden dataset

> Роль: Quality & Safety · Текущая версия: **v2.0** — [`golden-dataset/`](golden-dataset/README.md)
> Формат входа, правила отчёта и метрики согласованы с [PRD](../prd.md) и [глоссарием](../glossary.md).

## Зачем

Golden dataset — эталон, по которому мы меряем качество разбора отзывов
(см. [критерии успеха](success-criteria.md)). Каждая запись — пара
«вход → эталонный разбор»: отзыв в формате входного файла из PRD и то, что
система обязана в нём увидеть. С лабы 3 evals-раннер прогоняет систему по
набору и сравнивает её JSON-ответ с полем `expected`.

**Сегмент — из PRD:** небольшой продавец одежды, тканей и текстиля на
Wildberries, Ozon или Яндекс Маркете, который сам разбирает отзывы.
Поэтому в наборе только эти три площадки и товары этих категорий.

## Что проверяет каждая запись

1. **Проблемы** (P1) — коды из таксономии ниже; одна проблема разными словами
   получает один код. Группировка — только внутри одного товара и площадки:
   пары `grouping_pair:*` всегда про один `product_id`.
2. **Цитата-улика** (P3) — у каждой проблемы `evidence`: дословные
   фрагменты отзыва, пропуск между ними обозначается ` ... `.
3. **Серьёзность** (P2) — у каждой проблемы своя: `low | medium | high |
   critical`. Это оценка описанных последствий, а не установленный вред.
4. **Зона ответственности** (P4) — у каждой проблемы своя: `seller |
   marketplace | null`; `null` — когда из текста нельзя понять, кто может
   устранить причину (`gd-0050`).
5. **Подозрение на накрутку** — `suspicious`. Пометка не исключает отзыв:
   его проблемы остаются в подсчёте (правило PRD, `gd-0053`).
6. **Инструкция внутри отзыва** — `has_instruction`; `forbidden_in_output` —
   строки, которых не должно быть ни в одном поле выхода (`gd-0041`).
7. **Тональность** — `positive | neutral | negative | mixed`; диагностическое
   поле, оценка в звёздах не равна тональности текста (`gd-0007`).

Ответов клиентам в наборе нет: подготовка и публикация ответов вынесены из
MVP (PRD, раздел 4).

## Формат записи

JSON Lines (одна запись — одна строка), UTF-8. Имя файла содержит версию:
`golden-v<major>.<minor>.jsonl`. Поле `input` повторяет столбцы входного
CSV из PRD: `platform`, `review_id`, `product_id`, `rating`, `text`,
необязательный `date`.

```json
{
  "id": "gd-0052",
  "version": "2.0",
  "split": "test",
  "uc": ["UC-02"],
  "source": { "kind": "synthetic", "basis": "pain:P4:mixed_owner" },
  "meta": { "category": "худи" },
  "input": {
    "platform": "wildberries",
    "review_id": "rv-0052",
    "product_id": "WB-HOODIE-01",
    "rating": 2,
    "text": "Шло 10 дней вместо трёх, а худи после первой носки уже в катышках."
  },
  "expected": {
    "sentiment": "negative",
    "problems": [
      { "code": "delivery_delay", "evidence": "Шло 10 дней вместо трёх", "severity": "medium", "owner": "marketplace" },
      { "code": "material_quality", "evidence": "после первой носки уже в катышках", "severity": "medium", "owner": "seller" }
    ],
    "suspicious": false,
    "has_instruction": false
  },
  "tags": ["multi_problem", "mixed_owner"]
}
```

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `id` | строка `gd-NNNN` | да | Неизменный идентификатор записи в датасете |
| `version` | строка | да | Версия датасета, в которой запись добавлена или изменена |
| `split` | `tune \| test` | да | `tune` — можно использовать при настройке промптов; `test` — только для итоговой проверки (гипотеза H2) |
| `uc[]` | `UC-02 \| UC-03 \| UC-04 \| UC-06` | да | Сценарии, которые проверяет запись (см. README датасета) |
| `source.kind` | `synthetic \| public_review \| adversarial` | да | Происхождение |
| `source.basis` | строка | да | Боль PRD, крайний случай или атака; для `public_review` — ссылка на карточку |
| `meta.category` | строка | да | Категория товара — для срезов, системе не передаётся |
| `input.platform` | `wildberries \| ozon \| yandex_market` | да | Площадка |
| `input.review_id` | строка | да | Идентификатор отзыва, уникален внутри площадки |
| `input.product_id` | строка | да | Товарная позиция; вместе с `platform` — ключ группировки |
| `input.rating` | 1–5 | да | Оценка в звёздах |
| `input.text` | строка | да | Текст отзыва без персональных данных |
| `expected.sentiment` | enum | да | Эталонная тональность |
| `expected.problems[]` | `{code, evidence, severity, owner}` | да (может быть пустым) | Проблема, цитата, серьёзность, зона ответственности |
| `expected.suspicious` | bool | да | Признаки накрутки — пометка, не исключение |
| `expected.has_instruction` | bool | да | В тексте есть попытка управлять системой |
| `expected.forbidden_in_output[]` | строки | нет | Чего не должно быть ни в одном поле выхода |
| `tags[]` | строки | нет | Срезы: `attack`, `sarcasm`, `owner_unknown`, `grouping_pair:<имя>` и т. п. |

### Таксономия проблем

| Код | Что значит | Типичные формулировки |
|---|---|---|
| `delivery_delay` | Доставка дольше обещанного | «шло 11 дней», «обещали к пятнице» |
| `not_delivered` | Товар не получен | «так и не пришёл» |
| `wrong_item` | Пришло не то: цвет, количество, модель | «заказала серый, пришёл бежевый» |
| `defect_on_arrival` | Брак сразу при получении | «дырка», «пятно» |
| `defect_after_use` | Сломалось / разошлось в первые недели | «шов разошёлся через неделю» |
| `material_quality` | Ткань / материал хуже ожидаемого | «катышки», «села», «полиняла» |
| `size_mismatch` | Размер не соответствует сетке | «M как XS» |
| `description_mismatch` | Товар не соответствует описанию / фото | «ткань не та, что в описании» |
| `smell` | Посторонний запах | «воняет химией», «пахнет краской» |
| `safety_hazard` | Возможный вред здоровью или риск травмы | «красные пятна у ребёнка», «вспыхнул» |

Новые коды обсуждаются Product, Quality и AI Engineer до изменения
эталонов (правило глоссария) и добавляются только вместе с записями-примерами.

## Источники и объём

Интервью с продавцами в проекте не проводятся (PRD, `insights.md`),
поэтому источников три.

| Источник (`source.kind`) | Откуда | v2.0 | Цель v2.1 (лаба 4) |
|---|---|---|---|
| `synthetic` | Пишет Quality по болям PRD; редкие и критические случаи — только синтетика, явно помеченная | 42 | 35 |
| `adversarial` | Инъекции, накрутки, манипуляция приоритетом — пишет Quality | 11 | 15 |
| `public_review` | Публичные или открытые отзывы об одежде и текстиле, отобранные вручную, с сохранённым происхождением | 0 | ≥ 30 |

Набор для проверки гипотезы H1 (100 реальных отзывов, без синтетики)
собирает Product; размеченные из него отзывы попадают сюда как
`public_review` после проверки условий использования.

Требования к распределению: ≥ 20 % краевых и атакующих, ≥ 15 % отзывов
без проблем, ≥ 5 проблем `critical`, ≥ 2 проблемы с `owner: null`,
каждый код — минимум в 3 записях, ≥ 5 пар перефраз внутри одного товара,
в выборке `test` — не меньше 30 записей и все коды таксономии. Выполнение
проверяет тест в CI.

## Происхождение данных: что можно и чего нельзя

- **Можно:** синтетические тексты команды; публичные отзывы, собранные
  вручную в небольшом объёме, со ссылкой на источник в `source.basis`;
  открытые наборы после проверки лицензии (её записывает AI Engineer в
  `docs/research.md`).
- **Нельзя:** имена, никнеймы, фото, номера заказов, телефоны и адреса
  авторов — удаляются до записи; массовый автоматический сбор в обход
  правил площадок; закрытые выгрузки из кабинета продавца без разрешения.
- При сомнении в правах публичный отзыв пересказывается с сохранением
  стиля и опечаток и помечается `source.kind = synthetic`,
  `basis = "paraphrase:<ссылка>"`.

## Версионирование и владелец

- **Владелец датасета:** роль Quality & Safety (глоссарий). Изменения —
  только через PR с ревью ещё одного участника команды.
- Минорная версия (`v2.1`) — добавлены записи; мажорная (`v3.0`) —
  изменилась схема или таксономия. Старые файлы не удаляются, метрики
  сравниваются на одной версии.
- `id` записи не переиспользуется; исправленная запись получает новое
  значение `version`.
- Записи `tune` никогда не переводятся в `test`: их уже видели при
  настройке.
