# Лабораторная № 1: первые эксперименты Reviews Analyzer

Евгений Агарков · роль «Модель» / AI Engineer · 21.11.2026.

**Выполнено:** исследование, документарное сравнение трёх кандидатов, локальный
baseline, реальные пробы трёх промптов Qwen3-4B-4bit и записка с выбором подхода.
**181 реальная локальная генерация:** 180 в основных сериях + один smoke-запрос.
Облачная генерация не выполнялась, стоимость облачных API — **0 ₽**.
Это результат лабораторной по инициации, а не подтверждение готовности продукта.

## 1. Что проверяли

Можно ли извлечь проблемы, серьёзность, зону ответственности и точные цитаты из
русскоязычных отзывов? Достаточны ли правила? Что меняется от формулировки промпта?

Основание — боли P1–P5 и пределы 180 секунд / 50 ₽ на пакет из [PRD](../prd.md).
Подготовка и публикация ответов клиентам за пределами MVP, поэтому поля `reply`
эталона не генерировались и не оценивались.

## 2. Данные и честные ограничения

- Golden-v0.1: **12 синтетических отзывов, 12 эталонных пар «отзыв, код»**;
  исходный файл Quality не изменён.
- Challenge-v0.1: **8 новых синтетических отзывов, 5 эталонных проблем**, одно
  critical и три контроля без жалоб. Создан для поиска контрпримеров к правилам.
- Автор видел golden при разработке baseline; challenge также размечен автором.
  P2 создан после изучения ошибок P0/P1 на обоих наборах. Ни один набор нельзя
  считать независимым holdout или представительной выборкой отзывов продавцов.
- В наборе нет входных `product_id`/`review_id`; `id` записи используется только для
  сопоставления ответов. Корректность товарной группировки и частот не проверена.
- `gd-0002/gd-0003` имеют общий grouping-тег, но разные площадки: объединять их в
  одну товарную группу противоречит PRD. Классификацию общим кодом проверять можно.
- Серьёзность и owner пока относятся ко всему отзыву, а не к каждой проблеме.
- Один и тот же набор в трёх greedy-повторах — проверка воспроизводимости,
  не три независимых статистических наблюдения. Уникальных текстов всего 20.

В модель передавались только поля `input`, без `expected`, `tags` и `source`.
Ручная разметка не корректировалась ради улучшения показателей.

## 3. Проба правил

`rules-v0` — регулярные выражения для 10 кодов; цитата из исходного предложения.
`rules-v1` добавляет единственное исправление: исключение фразы «не линяет».

| Вариант | Набор | TP / FP / FN | Precision | Recall | Critical |
|---|---|---|---|---|---|
| rules-v0 | golden, 12 | 12 / 1 / 0 | 92,3% | 100% | 1/1 |
| rules-v1 | golden, 12 | 12 / 0 / 0 | 100% | 100% | 1/1 |
| rules-v1 | challenge, 8 | 0 / 1 / 5 | 0% | 0% | 0/1 |

В v0 «не линяет» породило жалобу; v1 исправил знакомый случай. Но «Запаха нет»
осталось ложной проблемой, а «рукава стали короче» и новые описания задержки/травмы
пропущены. 100% на знакомом наборе не означают устойчивость к перефразам.
[Ответы и метрики baseline](results/lab1/rules-v1/summary.json).

## 4. Реальный LLM-протокол

Использована локальная **mlx-community/Qwen3-4B-4bit** на Apple M1 Pro / 16 GB.
Ревизия: `4dcb3d101c2a062e5c1d4bb173588c54ea6c4d25`.
MLX 0.32.4, mlx-lm 0.32.2, Python 3.12.16; остальные версии зафиксированы
в [lock-файле](../../experiments/lab1/requirements-local.lock.txt).

Параметры: temperature=0 (greedy), seed=0, `enable_thinking=False`,
максимум 800 выходных токенов. Никакого дообучения, внешнего поиска или инструментов.
HF/Transformers работают offline; веса загружаются с локального диска.
Выбор greedy сделан для изоляции эффекта промпта; другие параметры и thinking-режим
не проверялись. Результаты не являются оценкой максимальных возможностей семейства Qwen.

Последовательность:

1. Smoke на одном golden-примере с P1: найден `delivery_delay`, схема корректна,
   но sentiment neutral вместо эталонного negative. Время 6,23 секунды,
   пик MLX 3,05 GB. Это проверка запуска, не оценка качества.
2. **P0:** минимальная инструкция с именами полей и кодов.
3. **P1:** определения, отрицания, граница недоверенного ввода; пример вывода
   содержал псевдосхему со строкой `seller|marketplace|null`.
4. **P2:** добавлен корректный JSON-пример с настоящим `null`, уточнены различия
   кодов, цитаты, критичность и флаг инструкции. Создан по замеченным ошибкам,
   без few-shot ответов из эталона.

Основные серии: `(12 + 8) × 2 промпта × 3 повтора = 120` для P0/P1,
затем `(12 + 8) × 1 × 3 = 60` для P2. Ответы и метки совпали между повторами;
latency варьировала. Для v1 runner сохранён
[точный снимок исходника](../../experiments/lab1/snapshots/local_trials-v1.py);
текущий runner добавляет выбор промптов и автоматическое определение оборудования.
Алгоритм генерации тот же; хеши каждой версии записаны в протоколах.

## 5. Результаты

**[Таблицы всех метрик, токенов, времени и памяти](local-results.md)** построены
из сохранённых JSON-артефактов, а не заполнены вручную.

Главное сравнение первого повтора (метки во всех трёх одинаковы):

| Промпт | Golden: precision / recall | Golden: схема | Golden: цитаты | Challenge: precision / recall |
|---|---|---|---|---|
| P0 | 76,9% / 83,3% | 100% | 12/13 | 42,9% / 60% |
| P1 | 75% / 75% | 83,3% | 8/12 | 66,7% / 80% |
| P2 | **83,3% / 83,3%** | **100%** | **8/12** | **66,7% / 80%** |

P2 дал 100% схемы и на challenge, а дословные цитаты там — 6/6. Но critical в P2 —
**0/1 на golden и 0/1 на challenge**. У P1 на challenge был правильный уровень
critical (1/1), хотя код проблемы оказался неверным. Нельзя выбирать P2 по одной
улучшившейся метрике и скрывать регрессию серьёзности.

Валидация схемы здесь проверяет обязательные поля, типы, перечисления и уникальность
кодов через evaluator; полноценный production JSON Schema-контракт ещё не внедрён.
Существование цитаты — подстрока исходника после нормализации пробелов, **с учётом
регистра**. Смысл цитаты оценивается отдельно. Неправильный JSON/тип не исправляется:
запись считается невалидной и её эталонные проблемы — пропущенными.
Нулевой знаменатель означает «нет данных», не 100%.

## 6. Разбор ошибок P0 → P1 → P2

- **Контракт:** P1 возвращал `"owner":"null"`, что является строкой. P2 с примером
  настоящего JSON null устранил эту ошибку на всех 20 текстах.
- **Отрицания:** P2 не нашёл запах в `ch-01`, но выдал `material_quality` на фразе
  «после стирки цвет прежний». Подмена одного ложного кода другим — не исправление.
- **Перефразы:** P2 нашёл задержку, дефект шва и несоответствие размера на challenge,
  где словарь пропустил всё. Но усадку в `ch-02` назвал `defect_after_use` вместо
  `material_quality`.
- **Сарказм:** P0 пропустил дефект `gd-0008`, P1 назвал его `description_mismatch`,
  P2 верно выдал `defect_on_arrival` и high.
- **Инъекция:** в `gd-0009` P2 поставил `has_instruction=true`, но перепутал
  неполучение с задержкой и добавил suspicious. Флаг обнаружения команды не означает
  безопасность всей системы. Публикации ответа и выполнения инструментов не было.
- **Критичность:** P2 не распознал `safety_hazard` в `gd-0011` и поставил high.
  В `ch-04` код safety_hazard правильный, но серьёзность также high вместо critical.
  Оба случая нарушают требование нулевых пропусков critical.
- **Цитаты:** в `gd-0003`, `gd-0009` и части `gd-0011` модель меняла начальные буквы
  на строчные. Совпадение после изменения регистра не засчитывалось.
  В `gd-0003` один и тот же фрагмент о расхождении с описанием использован также
  как основание material_quality: даже существующая строка может не доказывать код.
- **Owner:** запах товара отнесён к marketplace; это ошибка относительно эталона.
  `gd-0012` также расходится с разметкой. Не устанавливаем фактическую вину по отзыву:
  спорные случаи нужно разбирать с Product/Quality.
- **Тональность:** P2 пометил `gd-0001` mixed вместо negative. В отзыве есть и
  жалоба, и нейтрально-положительное замечание о белье, поэтому это полезный случай
  для ревью разметки. В данном прогоне эталон не менялся, ошибка учтена.

## 7. Выбранный подход и цена решения

Выбран путь **прямой LLM-промпт → структурированный разбор → внешние проверки →
агрегация обычным кодом**, без RAG и агента. Для учебных проб используется локальный
Qwen3-4B-4bit; P2 — исходная версия контракта для дальнейшего улучшения.
Окончательная production-модель **не выбрана**: текущие цели не выполнены.
[ADR-001 и альтернативы](../research.md#6-решение--adr-001).

Цена: около 3,3 GB локальной установки, до 3,24 GB памяти MLX, несколько секунд
на отзыв, падение качества на маленькой квантизованной модели и потребность в
независимом eval. Более подробный P2 увеличил время запроса и не решил критичность.
Облачные токены не оплачивались; электричество/амортизация не измерены.

API Яндекса отдельно подключён (GET списка моделей вернул HTTP 200, 19 моделей).
В связанном платёжном аккаунте отображалась платная версия без грантов; с учётом
разрешения пользователя «только бесплатно» генерация не выполнялась. Ключ хранится
локально в исключённом из Git файле, не входит в результаты и архив сдачи.

## 8. Что остаётся для следующих лабораторных

- Независимый набор Quality с ключами товаров и разметкой на уровне проблемы.
- Проверка альтернативного размера/режима модели и критических сигналов.
- Контракт точных span/offset цитат и внешние проверки, не маскирующие ошибки модели.
- Версии таксономии и обработка проблем вне известных кодов.
- Реальный отчёт: частоты, доли, сортировка critical, конкретные действия.
- Измерение полного пакета 100 отзывов: задержка 180 секунд пока **не подтверждена**.
  Линейная оценка из одиночных запросов также не является таким тестом.
- North Star с людьми, полноценные safety-evals, suspicious и macro-F1.

Это дальнейшая разработка, не скрытая имитация выполненной работы.
