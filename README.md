# smallindigroup
# Разбор отзывов клиентов — Reviews Analyzer

Проект курса «Системы искусственного интеллекта» (ВолгГТУ, магистратура).

## О проекте

Владельцы небольших компаний, продавцы маркетплейсов и менеджеры по работе с клиентами регулярно сталкиваются с большим количеством отзывов о товарах и услугах. При ручной обработке сложно своевременно обнаруживать повторяющиеся проблемы: покупатели могут описывать одну и ту же ситуацию разными словами, а важные замечания теряются среди большого количества сообщений.

**Reviews Analyzer** — система интеллектуального анализа клиентских отзывов, предназначенная для выявления повторяющихся проблем, определения их значимости и формирования рекомендаций по улучшению качества товаров и услуг.

В перспективе система позволит:

- Обрабатывать отзывы из открытых источников и поддерживаемых платформ.
- Анализировать тональность клиентских сообщений.
- Группировать семантически близкие жалобы, даже если они сформулированы по-разному.
- Определять частоту возникновения проблем и оценивать их приоритет.
- Формировать рекомендации для бизнеса и проекты задач по устранению выявленных недостатков.
- Подготавливать черновики ответов клиентам с обязательным подтверждением перед публикацией.

Особое внимание уделяется безопасности публичных ответов: содержание отзывов не должно использоваться как инструкция для системы, а отправка ответа клиенту должна выполняться только после подтверждения уполномоченным пользователем.

В лабораторной № 1 собран инфраструктурный каркас. Лабораторная № 2 описывает архитектуру MVP и добавляет локальный стенд с заглушками и UI-прототипом.

## Текущая реализация

На первом этапе подготовлено минимальное FastAPI-приложение со следующими маршрутами:

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/` | Информация о приложении и его версии |
| GET | `/health` | Проверка доступности API |
| GET | `/docs` | Автоматически генерируемая документация Swagger UI |

Endpoint `/health` возвращает:

```json
{
  "status": "ok"
}
```

Этот endpoint подтверждает доступность HTTP-приложения, но пока не проверяет соединение с PostgreSQL или внешними сервисами.

PostgreSQL разворачивается как отдельный контейнер и подготавливает инфраструктуру для будущего хранения отзывов, результатов анализа и связанных сущностей.

## Локальный запуск каркаса лабы 1

### Требования

Для запуска необходимы:

- Git;
- Docker с поддержкой Docker Compose;
- свободные порты `8000` и `5432`.

Для запуска приложения без Docker дополнительно требуется Python 3.12.

### Запуск через Docker Compose

**1. Клонировать репозиторий:**

```bash
git clone https://github.com/vstu-sii/stream-6-smallindigroup.git
cd stream-6-smallindigroup
```

**2. Запустить контейнеры из корня репозитория:**

```bash
docker compose up -d
```

При первом запуске Compose собирает образ FastAPI и запускает PostgreSQL с настройками по умолчанию. После обновления кода пересоберите образ командой `docker compose up --build -d`.

**3. Проверить состояние сервисов:**

```bash
docker compose ps
```

Контейнер API должен быть в состоянии `Up`, а PostgreSQL — в состоянии `Up (healthy)`.

**4. Проверить API:**

- Главная страница: http://localhost:8000/
- Health check: http://localhost:8000/health
- Swagger UI: http://localhost:8000/docs

### Управление контейнерами

Просмотр логов:

```bash
docker compose logs -f
```

Перезапуск:

```bash
docker compose restart
```

Остановка:

```bash
docker compose down
```

Остановка с удалением томов:

```bash
docker compose down -v
```

**Внимание:** последний вариант удаляет локальные данные PostgreSQL, хранящиеся в томе Compose.

## Запуск без Docker

Этот вариант предназначен для локальной разработки и тестирования API.

**1. Создать виртуальное окружение:**

```bash
python -m venv .venv
```

**2. Активировать окружение:**

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Linux/macOS:

```bash
source .venv/bin/activate
```

**3. Установить зависимости:**

```bash
python -m pip install -r backend/requirements-dev.txt
```

**4. Запустить приложение:**

```bash
cd backend
python -m uvicorn app.main:app --reload
```

Приложение будет доступно на http://127.0.0.1:8000.

Режим `--reload` предназначен только для разработки.

## Тестирование и качество кода

Все проверки выполняются из директории `backend`, чтобы Python корректно находил пакет `app`.

```bash
cd backend
```

Проверка качества кода:

```bash
python -m ruff check .
```

Проверка форматирования:

```bash
python -m ruff format --check .
```

Запуск тестов:

```bash
python -m pytest -v
```

Проверка сборки Docker-образа:

```bash
docker build -t reviews-analyzer:ci .
```

Тесты первого этапа проверяют доступность основных маршрутов и корректность HTTP-ответов.

## Непрерывная интеграция (CI)

Для автоматизации проверок используется GitHub Actions.

Конфигурация находится в `.github/workflows/ci.yml`.

CI предназначен для выполнения следующих операций:

1. Получение исходного кода из GitHub.
2. Подготовка Python 3.12.
3. Установка зависимостей приложения и разработки.
4. Проверка кода с помощью Ruff.
5. Проверка форматирования.
6. Запуск автоматических тестов.
7. Сборка Docker-образа.

Workflow настроен на запуск при создании или обновлении Pull Request в `main`, а также при отправке изменений в `main`.

Для выполнения требования лабораторной администратор репозитория должен включить обязательную проверку `Code Quality` для `main` в настройках защиты ветки GitHub.

Качество разбора проверяет отдельный workflow `.github/workflows/evals.yml`: на каждый PR и push в `main` — быстрый срез evals с порогами (`python -m pytest tests/evals -m fast`, PR красный при провале порога), ночью — полный прогон с отчётом. Чтобы провал порога блокировал мёрж, в защиту ветки добавляется проверка `Evals (fast slice)`. Подробнее — [tests/evals/README.md](tests/evals/README.md).

## Ветвление и Pull Request

Основная ветка проекта — `main`.

Изменения разрабатываются в отдельных ветках и передаются через Pull Request.

Примеры именования:

| Тип задачи | Пример |
|---|---|
| Лабораторная работа | `lab1-delivery-initiation` |
| Новая функциональность | `feature/review-analysis` |
| Исправление ошибки | `fix/health-endpoint` |
| Инфраструктура | `infra/docker-update` |
| Документация | `docs/readme-update` |

Для лабораторной № 1 ветка DELIVERY:

`lab1-delivery-initiation`

Заголовок Pull Request:

`Lab1: DELIVERY — Initiation Deliverables`

Перед слиянием изменений необходимо проверить результаты CI и убедиться в отсутствии случайно добавленных секретов.

Шаблон описания PR находится в `.github/PULL_REQUEST_TEMPLATE.md`.

## Переменные окружения

Для переопределения локальных настроек скопируйте `.env.example` в `.env` (`Copy-Item .env.example .env` в PowerShell или `cp .env.example .env` в Linux/macOS). При изменении параметров PostgreSQL обновите и `DATABASE_URL`. В сети Compose адрес базы — `db:5432`.

| Переменная | Назначение |
|---|---|
| `POSTGRES_DB` | Название базы данных |
| `POSTGRES_USER` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL |
| `DATABASE_URL` | Строка подключения к БД для будущей интеграции с API |

Реальный `.env` исключён из Git через `.gitignore`.

Пароли, API-ключи и другие секреты запрещено размещать в исходном коде и публичных файлах репозитория.
